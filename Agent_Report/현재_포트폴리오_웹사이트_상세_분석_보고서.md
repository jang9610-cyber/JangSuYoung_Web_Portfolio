# 현재 포트폴리오 웹사이트 상세 분석 보고서

- 작성일: 2026-07-29
- 분석 대상: 현재 포트폴리오로 공개·사용되는 웹페이지와 그 직접 종속 자산
- 분석 목적: 기존 포트폴리오가 어떤 정보 구조, 시각 언어, 상호작용, 기술 방식으로 만들어졌는지 파악하고 향후 3차 프로젝트 **「침몽도시 : 루시드다이버」** 웹페이지 제작의 기준을 정리
- 분석 방식: HTML/CSS/JavaScript 정적 소스, 페이지가 직접 참조하는 이미지·음원·PDF·Markdown 구조 분석

> **범위 제한**
>
> 사용자 요청에 따라 `기존_깃허브_프로젝트_문서/` 아래의 3차 프로젝트 문서 내용은 이번 분석에서 읽거나 근거로 사용하지 않았다.  
> 따라서 이 보고서의 3차 프로젝트 관련 제안은 오직 현재 포트폴리오 웹사이트가 이미 보여 주는 설계 철학과, 메인 허브에 공개된 최소 정보만을 바탕으로 한다. 실제 콘텐츠 확정은 이후 별도의 3차 프로젝트 문서 분석 단계에서 진행해야 한다.

## 1. 결론 요약

현재 사이트는 단순한 “프로젝트 목록형 포트폴리오”가 아니다. 각 게임의 대표 경험을 웹 UI 자체에 옮긴 **체험형 포트폴리오 허브**다.

- 메인 허브는 지원자 장수영의 정체성과 역량을 빠르게 요약하는 일반적인 채용 포트폴리오 구조를 사용한다.
- 1차 프로젝트 `Dark Dock` 상세 페이지는 게임의 핵심 메커니즘인 **어둠·시야 제한·손전등**을 마우스 조명 효과로 재현한다.
- 2차 프로젝트 `Hero Exposed` 상세 페이지는 게임의 핵심 설정인 **마왕물산 사내 전산망과 보안 심문**을 Windows 95 계열의 가상 OS로 재현한다.
- 두 상세 페이지는 시각 테마만 다른 것이 아니라, 정보 탐색 방식도 프로젝트 성격에 맞게 다르게 설계되어 있다.
- 반복되는 핵심 메시지는 “아이디어를 낸 사람”이 아니라 **기획 의도를 구현 가능한 명세·프로토타입·실제 결과로 연결하는 기획자**라는 점이다.
- 3차 프로젝트 페이지도 기존 상세 페이지의 외형을 복제하기보다, 루시드다이버만의 대표 플레이 경험을 웹 상호작용으로 번역해야 현재 포트폴리오의 일관성이 유지된다.
- 다만 2차 페이지는 몰입감과 콘텐츠 양이 매우 강한 대신, 초회 방문자의 인지 부담·모바일 사용성·성능·유지보수 비용이 크다. 3차 페이지는 **1차의 선형 가독성**과 **2차의 세계관 체험성**을 결합하는 방향이 가장 적합하다.

가장 중요한 해석은 다음 한 문장으로 정리된다.

> 이 포트폴리오의 목적은 “내가 무엇을 만들었다”를 나열하는 것이 아니라, “내가 게임의 핵심 재미를 어떻게 정의하고, 팀이 구현할 수 있는 자료로 만들고, 실제 결과까지 연결했는가”를 방문자가 직접 확인하게 하는 것이다.

## 2. 현재 사이트 구성과 배포 구조

### 2.1 페이지 구성

```text
/
├─ index.html                    루트 진입점, 메인 허브로 즉시 이동
├─ main-portfolio/
│  ├─ index.html                 인물·역량·3개 프로젝트 통합 허브
│  ├─ css/style.css
│  └─ js/main.js
├─ dark-dock/
│  ├─ index.html                 1차 프로젝트 상세 포트폴리오
│  ├─ css/style.css
│  ├─ js/app.js
│  ├─ assets/                    발표자료, 플로우차트, UI 이미지
│  ├─ docs/markdown/             페이지 안에서 읽는 기획 문서
│  └─ docs/original/             원본 문서 보관
├─ hero-exposed/
│  ├─ index.html                 2차 프로젝트 상세 포트폴리오
│  ├─ css/style.css
│  ├─ js/app.js
│  └─ assets/                    배경, 캐릭터, 음원, 발표자료
└─ assets/
   ├─ 프로젝트별 16:9 허브 이미지
   └─ 3차 프로젝트 제안서 PDF
```

### 2.2 실행 방식

현재 구현은 패키지 매니저, 프레임워크, 번들러, 서버 애플리케이션이 없는 정적 웹사이트다.

- HTML5 + Vanilla CSS + Vanilla JavaScript로 구성되어 있다.
- `package.json`, Vite/Webpack 설정, 서버 API, 데이터베이스가 없다.
- 모든 프로젝트는 상대 경로를 사용하므로 GitHub Pages의 하위 경로에서도 동작하도록 설계되어 있다.
- 루트 `index.html`은 세 가지 방법을 겹쳐 사용해 `main-portfolio/`로 진입시킨다.
  - `<meta http-equiv="refresh">`
  - JavaScript `window.location.href`
  - JavaScript가 꺼졌을 때 사용할 수 있는 일반 링크
- `.nojekyll`이 있어 GitHub Pages에서 Jekyll 처리를 우회한다.
- 현재 세 페이지가 참조하는 로컬 정적 경로는 모두 실제 파일이 존재한다.

이 방식의 장점은 배포가 단순하고, GitHub Pages와 잘 맞으며, 프레임워크 런타임 없이 페이지를 열 수 있다는 점이다. 반면 공통 컴포넌트나 콘텐츠 스키마가 없어서 새 프로젝트를 추가할 때 기존 HTML/CSS/JS를 복사하고 수동으로 수정할 가능성이 높다.

### 2.3 현재 소스 규모

| 페이지 | HTML | CSS | JavaScript | 구현 성격 |
|---|---:|---:|---:|---|
| 메인 허브 | 260줄 / 약 16KB | 534줄 / 약 11KB | 64줄 / 약 2.5KB | 일반적인 스크롤형 랜딩 페이지 |
| Dark Dock | 388줄 / 약 22KB | 702줄 / 약 17KB | 233줄 / 약 8KB | 선형 상세 페이지 + 탭 + 문서 뷰어 |
| Hero Exposed | 2,323줄 / 약 128KB | 3,317줄 / 약 70KB | 1,641줄 / 약 63KB | 데스크톱 OS를 흉내 낸 단일 페이지 애플리케이션 |

세 페이지 모두 정적 사이트지만, 2차 페이지는 사실상 별도 프레임워크 없이 만든 소형 웹 애플리케이션에 가깝다.

## 3. 메인 포트폴리오 허브 분석

분석 파일:

- `main-portfolio/index.html`
- `main-portfolio/css/style.css`
- `main-portfolio/js/main.js`

### 3.1 페이지의 역할

메인 허브의 역할은 상세 설명보다 **방문자 분류와 다음 행동 유도**다.

1. 누구인지 보여 준다.
2. 어떤 기획자인지 한 문장으로 정의한다.
3. 핵심 역량을 여섯 개 카드로 압축한다.
4. 세 프로젝트의 차이와 본인 역할을 비교하게 한다.
5. 관심 있는 프로젝트의 상세 페이지·빌드·외부 자료로 이동시킨다.
6. 마지막에 “3개 프로젝트에서 3개 콘셉트가 채택됨”이라는 대표 성과와 증거 링크를 다시 제시한다.

즉, 메인 허브는 전체 자료를 담는 곳이 아니라 **채용 담당자나 협업자가 1~2분 안에 지원자의 방향성을 이해하게 하는 요약 계층**이다.

### 3.2 정보 구조

페이지의 순서는 다음과 같다.

1. 고정 내비게이션
   - About
   - Skills
   - Projects
   - Notion Portfolio
2. Hero
   - 이름
   - 직무
   - 핵심 가치 제안
3. About Me
   - 기본 프로필
   - 기획 방식
   - 3회 콘셉트 채택 문장
4. Core Competencies
   - 게임 기획·시스템 설계
   - 수치 밸런싱
   - UI/UX·에셋 제작
   - 사운드 디렉팅
   - PM·마일스톤
   - AI 프롬프트 엔지니어링
5. Project Showcase
   - 3차 → 2차 → 1차 순서
6. 대표 성과와 증거 자료
   - 3차 기획 제안서
   - Figma 연출 프로토타입
   - Unity 실제 구현 결과
7. Footer

프로젝트가 최신순으로 배치되어 있으므로 3차 프로젝트가 완성되면 자연스럽게 첫 번째이자 가장 중요한 상세 페이지가 된다.

### 3.3 핵심 카피가 만드는 인물상

메인 페이지는 반복적으로 다음 정체성을 강화한다.

- “기획 의도를 구현 가능한 화면과 명세로 구체화”
- “시각·청각적 프로토타입 제작”
- “개발자가 구현 기준으로 활용할 수 있는 형태로 전달”
- “팀의 해석 차이와 소통 비용 감소”
- “콘셉트와 함께 구현 범위·상세 사양 제시”

이 문장들은 지원자를 순수 아이디어 기획자보다 다음과 같은 사람으로 정의한다.

- 시스템과 수치까지 내려가는 구체화 능력이 있는 기획자
- 아트·사운드·UI 프로토타이핑을 통해 의도를 보여 주는 기획자
- 문서를 팀 합의와 구현의 기준으로 쓰는 기획자
- 인력 이탈이나 일정 위험에 대응하는 PM형 기획자
- 결과물과 증거를 함께 제시하는 실무형 기획자

### 3.4 시각 디자인

전체 디자인은 어두운 배경 위의 보라·청록·주황 포인트를 사용하는 글래스모피즘 계열이다.

- 검은색에 가까운 배경으로 프로젝트 이미지와 강조색을 부각한다.
- 카드에 반투명 배경, 얇은 테두리, `backdrop-filter`를 사용한다.
- 본문은 `Noto Sans KR`, 시스템성 라벨은 `Share Tech Mono`를 사용한다.
- 보라는 개인 브랜드 및 기본 강조, 청록은 기술·신뢰, 주황은 성과·주의·증거에 가깝게 쓰인다.
- 프로젝트 이미지는 모두 1024×576의 16:9 비율로 통일되어 카드 비교가 쉽다.

메인 허브는 특정 게임 테마보다 “기술과 창작을 함께 다루는 기획자”라는 중립적 브랜드를 담당한다. 상세 페이지가 각 게임에 강하게 몰입하더라도 돌아올 수 있는 안정적인 기준점이다.

### 3.5 상호작용

JavaScript는 세 기능만 담당한다.

- 마우스를 따라가는 화면 전체 스포트라이트
- 프로젝트 카드의 3D 틸트와 마우스 위치 반사광
- `IntersectionObserver` 기반 스크롤 등장 애니메이션

상호작용의 강도는 상세 페이지보다 의도적으로 낮다. 이는 허브가 “체험 대상”보다 “길 안내와 비교”를 우선하기 때문이다.

### 3.6 반응형 처리

- 992px 이하에서 프로필 2열을 1열로 바꾼다.
- 768px 이하에서 내비게이션 링크를 숨기고, 제목·섹션 여백을 줄인다.
- 프로젝트 카드 버튼과 증거 표를 1열로 바꾼다.

기본적인 모바일 대응은 되어 있으나, 모바일 내비게이션이 별도로 제공되지 않아 메뉴가 완전히 사라진다. 페이지 자체는 스크롤로 읽을 수 있지만 구간 이동과 외부 포트폴리오 접근성이 낮아진다.

### 3.7 3차 프로젝트의 현재 자리

3차 프로젝트 카드는 이미 최상단에 준비되어 있다.

- 제목: `침몽도시 : 루시드다이버`
- 설명: 2.5D PvE 익스트랙션 액션 RPG
- 역할: PM·기획 총괄, SSOT 시스템 명세, 수치 밸런싱, UI/UX, 레벨 디자인
- 이미지: `assets/lucid_diver_banner.png`
- 상태: 상세 포트폴리오와 빌드 버튼 모두 비활성

또한 하단 증거 표의 첫 행에 3차 프로젝트 제안서가 이미 노출되어 있다. 이는 3차 페이지가 아직 없어도 메인 허브가 3차 프로젝트를 **지원자의 최신·대표 프로젝트로 선점**하고 있음을 의미한다.

3차 페이지 완성 시 필요한 최소 허브 변경은 다음과 같다.

- 비활성 “포트폴리오 대기” 버튼을 `../lucid-diver/` 링크로 전환
- 빌드가 실제 공개 가능한 경우에만 다운로드 버튼 활성화
- “진행 중” 기간과 팀 규모를 최종 상태로 갱신
- 페이지 상세 내용과 카드의 역할 태그·엔진 버전을 일치시킴
- 3/3 채택 주장과 제안서·결과물의 증거 연결을 더 명확히 함

## 4. 1차 프로젝트 `Dark Dock` 상세 페이지 분석

분석 파일:

- `dark-dock/index.html`
- `dark-dock/css/style.css`
- `dark-dock/js/app.js`

### 4.1 페이지의 핵심 콘셉트

Dark Dock 페이지는 일반적인 긴 스크롤 포트폴리오 구조를 유지하면서, 게임의 핵심인 제한된 시야를 **마우스를 따라 움직이는 손전등**으로 번역했다.

게임을 플레이하지 않아도 방문자는 첫 화면에서 다음을 즉시 체감한다.

- 매우 어두운 공간
- 마우스 주변만 밝아지는 시야
- 스캔라인과 비네팅
- 빨강·녹색·주황의 경고 UI
- 임무 보고서·작전 브리핑 같은 군사/산업 문서 어휘

상호작용이 장식에 그치지 않고 게임의 “어둠 속 탐색”을 설명하는 역할을 한다는 점이 중요하다.

### 4.2 정보 구조

고정 내비게이션과 본문 순서는 다음과 같다.

1. Hub 복귀
2. 요약
3. 게임 소개
4. 미디어
5. 기획 설계
6. 기획서 조회
7. UI/UX
8. 구현 분석
9. 개발 일지

본문의 서사 흐름은 다음과 같다.

| 단계 | 방문자에게 답하는 질문 |
|---|---|
| Hero | 어떤 게임이며 어떤 분위기인가? |
| 요약 | 기간, 팀, 엔진, 나의 역할은 무엇인가? |
| 게임 소개 | 핵심 재미와 플레이 제약은 무엇인가? |
| 미디어 | 실제로 구현되었는가? |
| 기획 설계 | 시스템과 수치는 어떻게 정의했는가? |
| 기획서 프리뷰 | 원본 문서 수준까지 검증할 수 있는가? |
| UI/UX | 화면 요소를 어떤 원칙으로 설계했는가? |
| 구현 분석 | 기획과 구현이 얼마나 일치했는가? |
| 개발 일지 | 일정·문제·의사결정을 어떻게 관리했는가? |

이 구조는 채용 포트폴리오 관점에서 매우 안정적이다. “요약 → 증거 → 상세 → 회고” 순으로 이해가 깊어진다.

### 4.3 프로젝트 설명 방식

Dark Dock는 게임 소개를 추상적 장르 설명으로 끝내지 않고 네 가지 핵심 플레이 제약으로 나눈다.

- 시야 제한
- 2슬롯 인벤토리
- 청각 기반 탐지
- 목표 아이템 소지로 인한 핸디캡

이후 플레이어·적·아이템 탭에서는 조작, HP, 이동속도, 총기 쿨다운, 재장전 시간, 투척력 등 구체적인 숫자를 공개한다. 이것은 “밸런싱을 했다”는 자기소개보다 훨씬 강한 증거다.

### 4.4 기획과 구현의 연결 방식

이 페이지에서 가장 포트폴리오다운 부분은 `기획 vs 실제` 비교 표다.

- 기획 수치
- 실제 구현 변수나 시스템명
- 일치 여부
- 기획보다 확장된 구현 항목

이 표는 메인 허브의 “기획-구현 싱크율” 메시지를 실제 사례로 입증한다. 또한 단순 성공 자랑이 아니라 Scene 단계가 4에서 5로 바뀐 항목을 경고 표시하고, 추가 구현도 분리한다. 변경 자체를 실패로 숨기기보다, 무엇이 달라졌는지 보여 주는 방식이다.

3차 프로젝트에서도 이 증거 구조는 반드시 재사용 가치가 높다.

```text
기획 의도
→ 상세 명세 또는 프로토타입
→ 실제 구현 화면·변수·동작
→ 일치/변경 여부
→ 변경 이유와 결과
```

### 4.5 문서 프리뷰 구현

Dark Dock는 CDN의 `marked.js`를 불러와 로컬 Markdown 파일을 페이지 안에서 렌더링한다.

동작 과정:

1. 문서 탭의 `data-doc`에서 Markdown 경로를 읽음
2. `fetch()`로 해당 파일을 불러옴
3. Markdown 내부의 상대 이미지 경로를 현재 웹 디렉터리에 맞게 보정
4. `marked.parse()`로 HTML 변환
5. 스크롤 가능한 문서 리더에 삽입
6. 문서 안 이미지와 정적 플로우차트에 확대 모달 연결
7. 배경 클릭이나 Escape 키로 모달 닫기

이 구현은 원본 문서의 존재를 외부 링크만으로 주장하지 않고, 페이지 안에서 즉시 검토하게 한다. 3차 프로젝트가 SSOT와 구현 명세를 핵심 역할로 내세우는 만큼 특히 적합한 패턴이다.

### 4.6 상호작용 목록

- 손전등과 커스텀 커서가 마우스를 추적
- 마우스 진입·이탈 시 조명과 커서 표시 상태 변경
- 스크롤 구간 등장 애니메이션
- 플레이어·적·아이템 탭
- 주차별 개발일지·이슈·의사결정 탭
- 내비게이션 부드러운 구간 이동
- Markdown 문서 탭과 동적 렌더링
- 플로우차트·문서 이미지 확대 모달
- Escape 키 모달 닫기
- 상호작용 요소에 커서를 올렸을 때 커스텀 커서 크기와 색 변화

### 4.7 강점

- 페이지 탐색이 선형이어서 초회 방문자가 이해하기 쉽다.
- 상호작용이 게임 메커니즘과 직접 연결된다.
- 프로젝트 설명, 수치, 문서, 구현 비교, 회고까지 증거 계층이 고르게 있다.
- 정적 HTML 기반이라 핵심 텍스트가 소스에 직접 존재하고 검색·복사·검토가 쉽다.
- Markdown 문서와 이미지 확대가 깊이 있는 검토를 지원한다.
- 상단에 Hub 복귀 버튼이 고정되어 전체 포트폴리오 맥락을 잃지 않는다.

### 4.8 한계와 기술 부채

#### 사용성과 접근성

- `body`와 링크·버튼에 `cursor: none`이 적용되어 JavaScript 오류 시 커서가 사라질 수 있다.
- 키보드 포커스 스타일과 `prefers-reduced-motion` 대응이 없다.
- 탭 버튼에 `role="tab"`, `aria-selected`, 패널 연결 정보가 없다.
- 모바일에서 8개의 내비게이션 링크를 축소만 하고 숨기거나 메뉴로 바꾸지 않는다. 768px 이하에서도 가로 공간이 부족할 가능성이 높다.
- 어두운 배경 위 `--text-dim: #666`은 일부 작은 본문에서 대비가 낮다.

#### 외부 의존성과 보안

- Google Fonts와 jsDelivr의 `marked.js`에 의존한다.
- `marked.min.js` URL에 명시적 버전이 없어 향후 라이브러리 변경으로 렌더링이 달라질 수 있다.
- Markdown 변환 결과를 별도 정화 없이 `innerHTML`에 넣는다. 현재 로컬 문서를 신뢰한다는 전제에서는 동작하지만, 향후 외부 입력이나 자동 동기화 문서를 받게 되면 스크립트 삽입 위험이 생긴다.
- 로컬 파일로 직접 열면 브라우저의 `fetch()` 제한으로 문서 프리뷰가 실패할 수 있다. GitHub Pages 같은 HTTP 환경에서는 정상 동작한다.

#### 유지보수

- HTML에 인라인 스타일과 인라인 마우스 이벤트가 남아 있어 CSS 규칙과 표현 책임이 분산되어 있다.
- JavaScript에는 현재 HTML에 존재하지 않는 진행률 바 `pb`, `pv` 참조와 애니메이션 코드가 남아 있다.
- 일반 탭 버튼과 문서 탭 버튼이 같은 `.tab-btn` 선택자에 걸리므로, 문서 탭 클릭 시 일반 탭 처리도 한 번 실행된다. 지금은 치명적이지 않지만 역할 분리가 불명확하다.
- `dark-dock/index.html` 끝부분에 불필요한 NUL 바이트 2개가 존재한다.
- 상세 페이지에는 엔진 버전이 `Unity 2022.3.62f3`로 표시되지만 메인 허브 카드에는 `Unity 2022.3f1`로 표시되어 표기가 일치하지 않는다.

## 5. 2차 프로젝트 `Hero Exposed` 상세 페이지 분석

분석 파일:

- `hero-exposed/index.html`
- `hero-exposed/css/style.css`
- `hero-exposed/js/app.js`

### 5.1 페이지의 핵심 콘셉트

Hero Exposed 페이지는 “게임 설명 페이지”가 아니라 **마왕물산 사내 전산망에 로그인해 기획자의 작업 파일을 탐색하는 가상 데스크톱**이다.

방문자는 다음 역할을 암묵적으로 부여받는다.

1. 로그인 화면에서 보안 전산망에 접속한다.
2. Windows 95 스타일 데스크톱에 진입한다.
3. 파일과 실행 프로그램을 열어 프로젝트를 조사한다.
4. 마왕의 지시문, 게임 시뮬레이터, 심문기, 기획 자판기, 직원 도감, 라디오를 체험한다.
5. 최종적으로 문서, 영상, 발표자료, 빌드를 확인한다.

게임의 “서류 대조·심문·가짜 직원 판별” 구조를 포트폴리오 탐색 행위와 겹치게 만들었다. 세 페이지 중 세계관과 UI의 결합도가 가장 높다.

### 5.2 화면 계층

#### 진입 계층

- `마왕 OS v1.00` 로그인 창
- 읽기 전용 사용자 이름과 비밀번호
- CONNECT 버튼
- PC 최적화 안내

CONNECT를 누르면 부팅음과 함께 로그인 화면이 사라지고, 데스크톱과 작업 표시줄이 나타난다.

#### 데스크톱 핵심 탐색 7종

1. `★요약_포트폴리오.exe`
2. `보안주임_장수영.exe`
3. `사장실_특별지시.sys`
4. `마왕물산_보안데스크.exe`
5. `보안_작업_일지`
6. `인턴_웨어울프_심문기.exe`
7. `마왕물산_기획_자판기.exe`

#### 보너스 콘텐츠

- 사내 라디오
- 몬스터 직원 도감
- 최종 시연 영상
- Figma 시연 영상
- 최종 발표자료 PDF

#### 상세 문서 창

작업 일지 폴더 안에서 다음 문서 창을 연다.

- PM 기록
- 게임 기획·시스템 설계
- 비주얼 아트·UI/UX
- AI 프롬프트 설계
- 사운드 디렉팅
- 프로젝트 회고록

전체 창은 라디오 위젯을 포함해 19개다.

### 5.3 정보 탐색 문제를 해결한 장치

OS 메타포는 몰입감이 강하지만 “무엇부터 열어야 하는가”가 불명확할 수 있다. 현재 구현은 이를 두 장치로 보완한다.

#### 요약 포트폴리오

- 데스크톱에서 1번 번호와 노란색 강조
- “원클릭 추천” 말풍선
- 주요 성과·역할·영상·문서·갤러리를 하나의 큰 창에 통합

초회 방문자가 모든 아이콘을 탐색하지 않아도 핵심 내용을 볼 수 있도록 한 우회로다.

#### 탐색 가이드 패널

- 핵심 7개 항목을 권장 순서로 제시
- 보너스 콘텐츠를 별도 분리
- 열어 본 창을 방문 완료로 표시
- 핵심 탐색 진행률을 계산
- 항목을 클릭하면 해당 창을 직접 실행

이 패널은 복잡한 세계관 UI 위에 얹은 실질적인 사용 설명서다. 3차 페이지가 실험적 인터페이스를 선택한다면 이와 같은 **명시적인 빠른 탐색 경로**가 반드시 필요하다.

### 5.4 가상 OS 엔진

JavaScript는 일반 페이지 효과를 넘어 데스크톱 창 관리자를 직접 구현한다.

- 창 클릭 시 활성 상태와 `z-index` 갱신
- 제목 표시줄 드래그로 창 이동
- 닫기·최소화
- 작업 표시줄 탭 생성·활성화·제거
- 데스크톱 아이콘 더블클릭
- 768px 이하 터치 환경에서 단일 클릭 실행
- 시작 메뉴 토글
- 폴더 안 파일 클릭으로 하위 창 실행
- 창을 열 때 효과음
- 로그인 후 네 개 창을 시간차로 자동 실행

최대화 버튼은 외형만 존재하고 실제 최대화 동작은 연결되어 있지 않다. OS 메타포가 강하기 때문에 방문자는 작동을 기대할 가능성이 높다.

### 5.5 프로젝트 핵심 경험의 웹 번역

#### 게임 시뮬레이터

- 세 장의 배경 레이어를 겹쳐 게임 화면을 구성
- 가운데 창 영역을 `clip-path`로 뚫어 캐릭터가 보이게 함
- 7종 몬스터 중 하나가 무작위로 걸어 들어옴
- 정지 호흡 애니메이션과 종족별 대사 표시
- 이후 화면 밖으로 퇴장하고 다음 몬스터가 등장

사용자가 질문을 입력하면 실제 AI 응답을 흉내 내지 않는다. 대신 이 화면이 구동 예시임을 알리고 실제 빌드 다운로드 버튼을 강조한다. 즉, **가짜 기능을 구현한 척하지 않고 체험의 경계를 명시**한다는 점이 좋다.

#### 웨어울프 심문기

스트레스 슬라이더 값에 따라 세 상태가 바뀐다.

- 0~49: Normal
- 50~79: Flustered
- 80~100: Angry

표정 이미지, 상태 배지, 대사, 효과음이 함께 변경된다. AI 프롬프트와 감정 시스템 설계를 방문자가 작은 인터랙션으로 이해하게 한다.

#### 기획 자판기

8개 기획 산출물을 음료 캔으로 표현한다.

- 뽑기 버튼 클릭
- 자판기 효과음
- 배출 상태 메시지
- 선택한 문서명 표시
- GitHub 문서를 새 창으로 열기

딱딱한 문서 링크 목록을 게임 세계관 안의 보상 행동으로 바꾼 사례다.

#### 직원 도감

- 7종 캐릭터 선택
- Normal/Nervous/Angry 표정 전환
- 부서·성격·프롬프트 설계 설명 표시

직접 제작한 캐릭터 자산과 AI 페르소나 설계를 동시에 보여 준다.

#### 사내 라디오

- 12곡 재생 목록
- 재생·일시정지·정지·이전·다음
- 볼륨, 탐색 바, 현재 시간·총 시간
- 곡 종료 후 다음 곡 자동 재생
- 메인 라디오 창을 닫으면 미니 위젯으로 전환

사운드 디렉팅을 텍스트 설명이 아닌 실제 청취 경험으로 증명한다.

#### 사장실 특별지시

- 타이핑 애니메이션
- 종족과 일자별 감별 지침 아코디언
- 기밀 문서·도장·경고 문구 연출

게임의 규칙과 블랙코미디 세계관을 동시에 설명한다.

### 5.6 콘텐츠가 증명하는 역량

Hero Exposed 페이지는 역량을 각각 독립된 “프로그램”이나 “파일”로 분해한다.

| PM | 6주 마일스톤, 역할 변천, 위기 대응, 성과 수치 |

| 아트 | 캐릭터 원화·표정 갤러리 |
| 사운드 | 12트랙 라디오와 씬별 배치 설명 |
| 결과물 | 영상, PDF, 빌드, 저장소 링크 |
| 회고 | 주차별 성과, 도전, 배운 점, 아쉬운 점 |

콘텐츠의 넓이는 “멀티 롤을 소화하는 밸런스형 기획자”라는 메인 허브의 메시지를 가장 강하게 뒷받침한다.

### 5.7 시각 디자인

- Windows 95 계열의 청록 데스크톱, 회색 창, 남색 제목 표시줄
- 픽셀 폰트와 시스템 폰트의 혼합
- 입체 테두리, 눌리는 버튼, 작업 표시줄, 시작 메뉴
- CRT 스캔라인과 화면 비네팅
- 마왕물산 세계관에 맞춘 파일명과 프로그램명
- 실제 캐릭터 스프라이트와 3중 배경 레이어

이 페이지는 “예쁜 레트로 디자인”보다 **프로젝트의 UI 언어를 포트폴리오의 운영체제로 확장**한 것이 핵심이다.

### 5.8 성능과 자산 구조

`hero-exposed/` 전체는 약 108.55MiB다.

- MP3 12개: 약 72.16MiB
- PNG 43개: 약 31.24MiB
- 발표 PDF: 약 4.83MiB
- HTML/CSS/JS: 약 0.25MiB

초기 코드가 명시적으로 미리 불러오는 이미지 13개만 약 17.34MiB다. 여기에 HTML, CSS, 폰트, 추가 배경·썸네일이 더해진다.

YouTube는 초기 iframe 대신 썸네일 facade를 표시하고 사용자가 클릭할 때 iframe으로 교체하므로 초기 외부 요청을 줄이려는 최적화가 적용되어 있다. 그러나 캐릭터와 배경 이미지의 초기 preload가 무겁고, MP3는 압축 용량이 크다.

### 5.9 강점

- 포트폴리오 형식 자체가 프로젝트의 독창성과 UI/UX 기획 능력을 증명한다.
- 텍스트, 이미지, 음원, 영상, PDF, 빌드가 하나의 세계관 안에 통합되어 있다.
- “요약 창”과 “탐색 가이드”로 복잡한 구조의 이탈 위험을 일부 보완했다.
- 실제 AI를 연결하지 않은 웹 예시의 한계를 명확히 밝히고 빌드로 유도한다.
- PM·기획·아트·사운드·프롬프트를 각각 체험 가능한 증거로 바꿨다.
- 방문 여부와 진행률을 표시해 탐색 동기를 만든다.

### 5.10 한계와 기술 부채

#### 인지 부담

- 로그인 후 0.45초부터 1.95초 사이에 사장실, 라디오, 게임, 요약 창 네 개가 연속으로 열린다. 첫 방문자는 화면이 풍부하다고 느끼는 동시에 어디를 봐야 할지 혼란스러울 수 있다.
- 핵심 창 7개와 보너스 창 5개, 하위 문서 창 6개가 있어 전체 콘텐츠를 다 확인하기 어렵다.
- 중요한 정보가 여러 창과 요약 창에 중복되어 수정 시 불일치 가능성이 높다.

#### 모바일과 키보드 접근성

- 페이지 전체가 `overflow: hidden`인 데스크톱 모델이라 모바일의 자연스러운 문서 스크롤과 맞지 않는다.
- 600px 이하에서 창 폭과 레이아웃을 줄이지만, 복잡한 창 내부 표·갤러리·PDF·미디어는 여전히 PC 중심이다.
- 데스크톱 아이콘은 `div`이며 키보드 포커스와 Enter 실행이 없다.
- PC에서는 더블클릭이 기본 실행 방식이라 웹 사용 관습과 다르다.
- 여러 창 버튼에 접근성 라벨이 있지만, 일부 최소화·최대화·닫기 버튼에는 라벨이 빠져 있다.
- 드래그, 아이콘 실행, 작업 표시줄 탭에 키보드 대체 수단이 없다.
- 움직임 감소 설정 대응이 없다.

#### 기능 일관성

- 모든 창에 최대화 버튼 모양이 있지만 최대화 로직은 없다.
- YouTube facade가 실제 iframe으로 교체된 후, 초기 변수에 저장된 iframe 참조는 계속 `null`일 수 있다. 따라서 별도 플레이어 버튼이 동적으로 생성된 iframe을 안정적으로 제어하지 못할 가능성이 있다.
- YouTube 명령을 `postMessage`로 보내지만 동적 iframe URL에 `enablejsapi=1`이 포함되지 않아 재생·일시정지 제어가 브라우저와 플레이어 상태에 따라 기대대로 작동하지 않을 수 있다.
- 창 최소화 시 작업 표시줄 탭은 남지만, 일부 미디어 정지는 첫 번째 CCTV 창만 특별 처리한다.

#### 유지보수

- HTML 한 파일에 2,323줄의 콘텐츠와 203개의 인라인 스타일이 있다.
- CSS는 3,317줄, JavaScript는 1,641줄이며 모든 기능이 단일 파일에 결합되어 있다.
- 동일한 직원 갤러리가 일반 창과 요약 창에 별도 마크업·별도 이벤트로 중복된다.
- 창 정의, 가이드 정의, 아이콘 정의가 서로 다른 위치에 수동으로 반복되어 새 창 추가 시 세 곳 이상을 함께 수정해야 한다.
- 일부 음향 효과 함수는 호출할 때마다 새 `AudioContext`를 생성한다. 장시간 사용 시 불필요한 리소스 사용 가능성이 있다.
- 외부 링크가 다수의 긴 URL로 HTML에 직접 삽입되어 관리가 어렵다.

#### 성능

- 초기 preload 약 17.34MiB는 모바일·저속 환경에서 크다.
- 12개 MP3 중 가장 큰 파일은 약 9.86MiB이고 전체 음원이 약 72MiB다.
- 캐릭터 PNG 일부는 한 장에 약 1MiB 이상이다.
- WebP/AVIF, 오디오 비트레이트 조정, 필요 시 로딩 전략을 적용할 여지가 크다.

## 7. 현재 구현으로 추론되는 사용자 의도

### 7.1 최우선 의도: “기획을 구현까지 연결하는 사람”으로 보이고 싶다

현재 사이트에서 가장 자주 반복되는 것은 게임 장르나 특정 툴 이름이 아니다. 다음 연결 구조다.

```text
아이디어 제안
→ 팀 설득과 채택
→ 구현 가능한 명세
→ 프로토타입
→ 개발 결과
→ 비교·검증
→ 회고와 개선
```

즉, 지원자가 전달하려는 핵심은 창의성 하나가 아니라 **창의성을 팀의 실행으로 바꾸는 능력**이다.

### 7.2 문서보다 결과, 결과보다 연결 관계를 보여 주고 싶다

사이트에는 문서 링크가 많지만 문서만 나열하지 않는다.

- Dark Dock는 문서를 웹에서 바로 렌더링하고 구현 비교 표를 붙인다.
- Hero Exposed는 문서를 자판기·폴더·프로그램으로 바꾸고 영상·음원·갤러리와 연결한다.
- 메인 허브는 제안서, Figma, Unity 결과물을 한 표에 묶는다.

이 구조는 “문서를 많이 만들었다”가 아니라 **문서가 실제 구현 과정에서 어떤 역할을 했는지**를 보여 주려는 의도다.

### 7.3 프로젝트마다 다른 기획적 감각을 보여 주고 싶다

1차와 2차 상세 페이지는 동일 템플릿에 색만 바꾼 구조가 아니다.

- 1차: 공포 서바이벌의 시야 제한과 임무 보고서
- 2차: 블랙코미디 AI 추리 게임의 사내 OS와 보안 심문

이는 프로젝트별 핵심 재미를 UI 콘셉트로 추출하는 능력, 즉 **메타 레벨의 UX 기획 능력**까지 포트폴리오로 보여 주려는 선택이다.

### 7.4 멀티 롤이 산만함이 아니라 “통합 설계 능력”으로 읽히길 원한다

기획, PM, UI/UX, 그래픽, 사운드, AI를 모두 했다는 사실은 자칫 직무 초점이 흐린 것으로 보일 수 있다. 현재 메인 카피는 이를 다음과 같이 정리한다.

- 중심축은 시스템 기획
- 다른 역량은 기획 의도를 시각·청각적 프로토타입으로 구체화하기 위한 수단
- 최종 목적은 팀의 해석 차이와 소통 비용 감소

따라서 3차 페이지도 역할을 많이 나열하기보다, 각 역할이 **하나의 기획 의도를 구현으로 연결하는 과정에서 어떤 기능을 했는지** 보여 줘야 한다.

### 7.5 대상 방문자는 채용 담당자와 실무 면접관 모두다

- 메인 허브와 요약 창은 짧게 보는 채용 담당자용이다.
- 수치, 플로우차트, Markdown, GitHub, 프롬프트 구조는 깊게 검증하는 실무 면접관용이다.
- 영상·빌드·상호작용은 결과를 빠르게 체험하려는 방문자용이다.

따라서 현재 사이트는 의도적으로 **요약 계층과 심층 계층을 동시에 보유**한다.

## 8. 3차 프로젝트 웹페이지가 맡아야 할 역할

3차 페이지는 단순히 세 번째 상세 페이지를 채우는 것이 아니다. 현재 메인 허브에서 가장 먼저 보이는 최신 프로젝트이며, 다음 주장을 완성해야 한다.

1. 3회의 프로젝트 모두에서 콘셉트가 채택되었다.
2. 프로젝트 규모가 커져도 기획 총괄과 PM 역할을 수행할 수 있다.
3. SSOT, 시스템 명세, 수치, UI/UX, 레벨 디자인을 하나의 기준 아래 관리할 수 있다.
4. 앞선 두 프로젝트에서 보여 준 “기획-구현 연결”을 더 성숙한 형태로 반복할 수 있다.

### 8.1 반드시 유지해야 할 기존 포트폴리오의 문법

#### 프로젝트 고유 경험을 웹 인터랙션으로 번역

Dark Dock의 손전등, Hero Exposed의 사내 OS처럼 3차 프로젝트만의 대표 경험이 첫 화면과 핵심 상호작용에 반영되어야 한다.

현재 메인 허브에 공개된 정보만 보면 활용 가능한 방향은 다음 수준까지다.

- 현실과 왜곡된 꿈의 중첩
- 침몽도시 탐사
- 심상핵 회수
- 탈출
- 일상 기물을 즉석 무장으로 사용하는 드림 포지드

다만 어떤 UI와 상호작용이 실제 게임 경험을 가장 정확히 대표하는지는 이후 프로젝트 문서를 읽은 뒤 결정해야 한다. 현재 단계에서 구체적인 시스템이나 수치를 창작해서는 안 된다.

#### 빠른 요약과 깊은 탐색을 동시에 제공

첫 화면 또는 첫 번째 섹션에서 최소한 다음 정보가 즉시 보여야 한다.

- 한 줄 게임 정의
- 기간·팀 규모·엔진
- 본인 역할
- 핵심 기여 3~5개
- 가장 강한 결과물 1개
- 상세 탐색과 빌드/영상으로 가는 CTA

이후 심층 구간에서 문서와 구현 증거를 제공해야 한다.

#### 증거 사슬을 보여 주기

3차 프로젝트는 다음 다섯 단계가 한 화면 흐름에서 연결되어야 한다.

1. 왜 이 콘셉트를 제안했는가
2. 무엇을 기준 문서와 시스템 명세로 정의했는가
3. 팀에 어떤 프로토타입·도표·UI 흐름으로 전달했는가
4. 실제 빌드에 무엇이 구현되었는가
5. 무엇이 바뀌었고, 왜 바뀌었으며, 결과는 어땠는가

#### 팀 성과와 개인 기여를 분리

현재 사이트는 본인 역할을 강하게 제시하지만, 3차는 5인 프로젝트인 만큼 다음 표기가 더 중요하다.

- 팀 전체 결과
- 본인이 직접 소유한 산출물
- 공동 설계 항목
- 제안자와 최종 결정권자
- 구현 담당자와 협업 방식

이 분리가 명확해야 기여도가 과장처럼 보이지 않고 PM·총괄 역량이 더 설득력 있게 보인다.

### 8.2 추천 정보 구조

이 구조는 현재 웹페이지만 분석해 도출한 초안이며, 실제 항목명과 내용은 3차 문서 분석 후 확정한다.

1. **몰입형 Hero**
   - 프로젝트 고유 연출
   - 한 줄 게임 정의
   - 즉시 요약 보기 / 체험 시작 두 경로
2. **프로젝트 요약**
   - 기간, 팀, 엔진, 장르, 플랫폼
   - 본인 역할과 기여 범위
3. **문제 정의와 콘셉트 제안**
   - 제안 배경
   - 핵심 재미
   - 채택 과정과 판단 근거
4. **코어 플레이 루프**
   - 진입 → 탐색 → 전투/수집 → 탈출 등의 실제 흐름
   - 인터랙티브한 단계 전환
5. **시스템 설계**
   - SSOT 구조
   - 주요 시스템 관계
   - 수치와 상태 변화
6. **UI/UX와 프로토타입**
   - Figma/화면 흐름
   - 프로토타입과 실제 구현 비교
7. **레벨 디자인**
   - 목표, 동선, 리스크·보상, 공간 설계
8. **기획 대 구현**
   - 기획 사양
   - 실제 결과
   - 변경 사항과 이유
9. **PM과 의사결정**
   - 일정
   - 역할 배분
   - 범위 조정
   - 이슈 해결
10. **결과물**
    - 시연 영상
    - 빌드
    - 발표자료
    - 선별된 문서
11. **회고**
    - 성과
    - 실패 또는 한계
    - 다음 개선
12. **허브 복귀와 연락**

### 8.3 인터랙션 강도 권장

3차 페이지는 Hero Exposed처럼 모든 콘텐츠를 별도 창으로 분리하기보다 다음 방식이 적합하다.

- 기본 정보는 Dark Dock처럼 세로 스크롤로 항상 읽을 수 있게 둔다.
- 한두 개의 대표 시스템만 프로젝트 고유 인터랙션으로 깊게 체험시킨다.
- 요약과 실제 증거는 클릭을 요구하지 않고 노출한다.
- 원본 문서, 도표, 비교표는 탭·확대·필터로 깊이를 제공한다.
- 페이지 진입 직후 여러 팝업을 자동으로 띄우지 않는다.
- 인터랙션은 “멋있어 보이는 효과”보다 기획 내용을 이해시키는 도구로 제한한다.

이렇게 하면 1차의 가독성과 2차의 독창성을 모두 계승할 수 있다.

## 9. 3차 구현 전에 정리할 공통 기술 기준

### 9.1 공통 메타데이터

프로젝트마다 다음 값을 한 곳에서 관리할 수 있는 구조가 필요하다.

- 프로젝트명
- 부제
- 기간
- 팀 규모
- 엔진 버전
- 역할
- 장르
- 영상 URL
- 빌드 URL
- 문서 URL
- 허브 카드 이미지

현재는 같은 정보가 README, 메인 허브, 상세 페이지에 중복되어 엔진 버전이나 상태가 어긋날 수 있다.

### 9.2 재사용 가능한 UI 패턴

프레임워크를 도입하지 않더라도 최소한 다음 코드는 공통 모듈로 분리할 가치가 있다.

- 스크롤 Reveal
- 탭
- 이미지 라이트박스
- 미디어 facade
- Markdown 문서 리더
- 허브 복귀 버튼
- 프로젝트 메타 정보 표
- 기획 대 구현 비교 표
- 접근 가능한 모달 닫기

3차 페이지를 복사·붙여넣기로 만들 경우 동일 기능이 세 번째 방식으로 또 생기고, 수정 비용이 급격히 증가한다.

### 9.3 성능 예산

권장 기준:

- 첫 화면에 꼭 필요한 이미지만 preload
- 배경·캐릭터 PNG는 WebP/AVIF 변환 검토
- 긴 음원은 웹용 비트레이트로 재인코딩
- iframe은 클릭 시 로드
- 화면 아래 이미지는 `loading="lazy"`
- PDF와 원본 문서는 사용자 요청 시 로드
- 3차 페이지의 초기 필수 자산은 현재 Hero Exposed의 17.34MiB preload보다 크게 낮출 것

### 9.4 접근성 기준

- 모든 클릭 요소는 `button` 또는 `a` 사용
- 키보드 Enter/Space 실행 지원
- 명확한 `:focus-visible`
- 탭에 ARIA 역할과 선택 상태 제공
- 모달 열 때 포커스 이동, 닫을 때 원위치 복원
- Escape 닫기
- `prefers-reduced-motion`에서 자동 이동·깜빡임·타이핑 최소화
- 커스텀 커서 실패 시 기본 커서 유지
- 본문과 보조 텍스트 대비 확보
- 모바일에서는 별도의 단순 탐색 경로 제공

### 9.5 콘텐츠 신뢰성 기준

- 숫자와 성과는 근거 링크 또는 화면을 인접 배치
- 팀 결과와 개인 기여 구분
- 프로젝트 상태, 기간, 엔진 버전 일치
- 구현되지 않은 기능은 구동 예시·목업·예정 상태를 명확히 표시
- 문서 전체를 노출하기보다 주장과 직접 연결되는 대표 페이지를 선별
- “3/3 채택”, “90%+ 싱크” 같은 강한 수치는 계산 기준 또는 사례 표와 연결

## 12. 최종 판단

현재 포트폴리오는 이미 분명한 차별점이 있다.

- 각 프로젝트의 핵심 경험을 웹 UX로 재구성한다.
- 기획 문서와 실제 결과물을 한 흐름 안에서 보여 준다.
- 시스템 기획을 중심으로 PM·UI/UX·그래픽·사운드·AI 역량을 통합한다.
- 실패나 변경도 의사결정 기록으로 바꾼다.

3차 프로젝트 페이지의 성공 기준은 Hero Exposed보다 기능이 많거나 더 화려한가가 아니다. 다음 세 가지가 동시에 만족되는가다.

1. **루시드다이버만의 핵심 경험이 첫 화면과 대표 인터랙션에서 느껴지는가**
2. **장수영의 기획이 팀의 구현으로 연결된 증거가 짧고 명확하게 보이는가**
3. **관심이 생긴 방문자가 SSOT·시스템·UI/UX·레벨 디자인·PM 기록까지 깊게 검증할 수 있는가**

따라서 가장 적합한 방향은 다음과 같다.

> **Dark Dock의 선형 가독성 + Hero Exposed의 프로젝트 고유 체험성 + 메인 허브의 명확한 직무 메시지**를 결합해, 3차 프로젝트를 현재 포트폴리오의 대표 사례로 완성한다.
